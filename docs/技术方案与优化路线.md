# 流式 ASR 助听字幕 Demo — 技术方案与优化路线

> 目标：在低端 Android 真机（Huawei MRD-AL00 / Helio P35，8×A53，Android 9）上验证量化流式 ASR 的可行性，产出一个可实时上屏字幕的 Demo，并系统探索精度 / 速度 / 体积的最优折中。

---

## 1. 技术选型

| 维度 | 选择 | 理由 |
|------|------|------|
| 推理框架 | sherpa-onnx 2.0.1 | 纯 C++ + ONNX Runtime，提供 Java JNI，无 AndroidX 依赖，int8 量化生态成熟 |
| 模型结构 | 流式 zipformer transducer | 支持 chunk 级流式解码，首字延迟可控 |
| 量化方式 | 逐组件混合精度（非全 int8） | 见 §3 量化隔离实验 |
| 解码方法 | greedy_search | 最快，无 beam 开销 |
| 端点检测 | rule1/2/3 三级 | rule2 终止静音 0.6s，兼顾灵敏度与误触 |
| Android UI | 纯 Java 手写（无 Compose/ViewBinding） | 避免依赖膨胀，APK 体积可控 |

### 1.1 候选模型对比（PC 端，200 条 AISHELL-3）

| 模型 | 体积 | CER(clean) | RTF | 备注 |
|------|------|-----------|-----|------|
| zh-14M int8 | 24MB | 12.36% | 0.052 | 速度最快，精度不足（同音字替换） |
| paraformer 流式 int8 | — | 11.27% | 0.317 | 非自回归，RTF 过高不采用 |
| **bilingual 混合精度** | **199MB** | **3.79%** | 0.137 | **精度最优，入选** |

噪声场景（babble）：

| 模型 | 10dB | 0dB |
|------|------|-----|
| zh-14M int8 | 17.04% | 68.31% |
| bilingual 混合 | 4.68% | 52.62% |

> 结论：bilingual 混合精度在干净与 10dB 噪声下均显著优于 14M；但 0dB 强人声干扰下两者都崩（CER>50%），需前置降噪。

## 2. 量化策略与逐组件隔离实验

### 2.1 问题发现

全 int8 的 bilingual 模型 CER 从 fp32 的 3.87% 暴增至 25.34%，且出现**重复循环**（如「漂亮漂亮亮主妇妇」「晚晚湘湘湘湘」）。直觉上"全 int8 更快"不成立，必须定位是哪个组件的 int8 导致退化。

### 2.2 隔离实验设计

固定 encoder 为 int8（省 141MB，必选），分别单独量化 decoder / joiner，以 `rep_ratio`（连续重复字符占比）直接度量重复循环：

| encoder | decoder | joiner | CER | rep_ratio | 重复句子 | 模型体积 |
|---------|---------|--------|-----|-----------|---------|---------|
| int8 | int8 | fp32 | **24.19%** | 11.72% | 324/536 (60%) | 198.2 MB |
| int8 | fp32 | int8 | **3.77%** | 1.24% | 44/536 (8%) | 189.8 MB |
| int8 | fp32 | fp32（基线） | 3.79% | — | — | 198.9 MB |
| int8 | int8 | int8（全 int8） | 25.34% | — | — | 189.0 MB |

各组件体积：

| 组件 | fp32 | int8 | 节省 |
|------|------|------|------|
| encoder | 314.8 MB | 173.5 MB | 141.3 MB |
| decoder | 13.2 MB | 12.5 MB | **0.7 MB** |
| joiner | 12.2 MB | 3.1 MB | **9.1 MB** |

### 2.3 结论

- **重复循环的根因是 decoder int8**：decoder 是自回归 RNN，每步输出喂回下一步，int8 舍入误差在反馈循环中累积放大，触发重复 token 的正反馈。而 decoder int8 仅省 0.7MB，毫无性价比。
- **joiner int8 完全安全**：joiner 只是 encoder+decoder 输出的非线性投影，无反馈回路，省 9.1MB 且 CER 不变。
- **最终方案：enc int8 + dec fp32 + join int8（189.8MB）**。

## 3. Android 端实现

### 3.1 模型打包

- 模型内嵌 `assets/model/`，首启解包到 `filesDir/model/`。
- 用 `LABEL.txt` 作为版本戳写入 `.stamp` 文件：换模型后整目录删除重建，避免新旧权重混用。
- `abiFilters 'arm64-v8a','armeabi-v7a'`：裁掉 x86/x86_64（仅模拟器用），省 69.2MB。
- `androidResources.noCompress 'onnx'`：避免二次拷贝，解包更快。
- APK 体积：**250.2 MiB**（assets 189.9MB + native 51.1MB + dex）。

### 3.2 UI（参考 voice-notepad.html 设计稿）

设计令牌从 `oklch` 转近似 sRGB：`#FCFCFD` 底色、`#2E6BE6` 主色、10/14 圆角、mono 数字。

组件：132dp 圆形录音键（录音时转 danger 红 + 160dp 脉冲环 1.6s、状态点 1.1s 呼吸）、27 根波形条、圆角转写卡 + LIVE 胶囊、mono 44sp 计时。

### 3.3 关键代码结构

```
MainActivity.java
 ├─ buildUi()            纯 Java 布局（无 XML）
 ├─ resolveModelFiles()  外部目录优先，否则解包 assets
 ├─ loadModel()          sherpa-onnx OnlineRecognizer 构建
 ├─ recordLoop()         麦克风实时字幕（每 100ms 一块）
 ├─ benchLoop()          文件基准（实时节奏喂块）
 └─ showCaption()        已定稿 FG 色 + 临时 MUTED + 青色光标 ▌
Ui.java                   设计令牌 + drawable 工厂
WaveformView.java         27 根波形条（idle/active 双态）
```

## 5. 解码瓶颈分析

### 5.1 参数扫描（bilingual enc/join int8 + dec fp32，10 条 AISHELL-3）

| threads | chunkMs | RTF | 解码 p95 | 首字 P50 | PSS |
|---------|---------|-----|---------|---------|-----|
| 1 | 100 | 1.044 | 473ms | 1306ms | 282MB |
| 2 | 100 | 0.757 | 371ms | 1085ms | 284MB |
| 3 | 100 | 0.657 | 323ms | 955ms | 283MB |
| **4** | **100** | **0.635** | **299ms** | 994ms | 283MB |
| 4 | 150 | 0.663 | 309ms | **850ms** | 287MB |
| 4 | 200 | 0.639 | 328ms | 972ms | 287MB |
| 4 | 100 | 0.639 | 309ms | 959ms | 285MB（xnnpack） |

### 5.2 瓶颈定位

1. **主瓶颈是 173MB 的 int8 encoder，且是内存带宽受限，不是算力受限。** Helio P35 是 8×A53（顺序执行、小缓存），encoder 权重每块都要从内存搬一遍，A53 的内存带宽喂不饱更多核心。证据：t1→t2 加速 27%，t2→t3 加速 13%，t3→t4 仅加速 3.4%——3 线程后基本到顶。

2. **decoder + joiner 占比极小**：decoder 13.2MB fp32、joiner 3.1MB int8，且每块只跑一次，不是瓶颈。

3. **chunk 大小对 RTF 影响很小**（c100=0.635 vs c200=0.639），因为总计算量不变；但 c100 的 p95 最低（299ms），c150 的首字延迟最好（850ms）。

4. **XNNPACK 无额外收益**——默认 ORT CPU EP 对 int8 已启用优化内核。

### 5.3 当前最优配置

- **threads=4**：RTF 最低（0.635），但 p95 仅比 t3 低 24ms，且更易热节流。
- **chunkMs=100**：p95 最低。若追求首字延迟可改 150ms（首字 850ms，p95 309ms）。
- 实际手机长时间运行建议 **threads=3**：RTF 仅多 0.022，留出 1 核给 AudioRecord/UI，减少抢占与热节流。

## 6. 后续优化方案（按投入产出排序）

### 6.1 低成本（已验证可行）

- **threads 4→3**：实时字幕场景下减少热节流和 UI 卡顿，RTF 代价 3.4%。
- **chunkMs 100→150**：首字延迟从 994ms 降到 850ms，p95 仅增 10ms，RTF 0.663 可接受。

### 6.2 中成本（需验证）

- **前置降噪 GTCRN**：解决 0dB 噪声场景 CER>50% 的致命问题，覆盖餐厅/多人场景。sherpa-onnx 内置 `OfflineSpeechDenoiserGtcrnModelConfig`，可串联在 ASR 前。
- **NNAPI provider 试验**：在支持的机型上可能有加速（Helio P35 不支持，需新机型验证）。
- **ONNX 图优化等级**：确认 `ORT_ENABLE_ALL` 已开启，尝试 `ORT_ENABLE_BASIC` 对比（某些小模型减少图变换开销）。

### 6.3 高成本/换模型

- **换更小模型**：要 RTF<0.4 必须换 14M 级（但 CER 升至 12%），或用 GTCRN 降噪后 14M 做噪声场景补偿。
- **模型蒸馏/剪枝**：对 bilingual encoder 做结构化剪枝，目标 100MB 以内，但精度可能下降 1-2 个点。
- **自研 int8 校准**：当前 decoder int8 用 sherpa 默认校准导致重复循环。若用感知量化（per-channel weight + 校准集）可能修复，但需改 sherpa-onnx 导出脚本，工作量大。

## 7. 后续扩展方向

### 7.1 功能扩展

- **双轨字幕**：已支持中文/英文双语模型，可加英文 UI 轨。
- **标点恢复**：sherpa-onnx 支持 `OnlinePunctuation`，可在字幕中加标点。
- **说话人分离**：多人场景下区分说话人（需额外 diarization 模型）。
- **字幕导出**：保存为 SRT/TXT，支持时间戳。
- **实时翻译**：ASR 后接 NMT，做同声传译。

### 7.2 工程化

- **模型按需下载**：首启从 CDN 拉模型，APK 降至 ~5MB。
- **多模型热切换**：UI 中切换 14M/bilingual，无需重启。
- **性能自适应**：根据设备 CPU 档位自动选 threads（低端机 t3，旗舰 t4）。
- **AB 测试框架**：已有 `modelDir` intent 支持，可扩展为远程配置下发。

### 7.3 无障碍场景深化

- **震动反馈**：端点定稿时短震，帮助听障用户确认。
- **关键词高亮**：自定义词典（如人名、地名）在字幕中高亮。
- **低延迟模式**：chunkMs 60ms，首字 <700ms（牺牲部分 RTF）。
- **离线唤醒词**：配合 KWS 实现免手动启动。

## 9. 结论

- **精度**：bilingual 混合精度（enc int8 + dec fp32 + join int8）在 AISHELL-3 上 CER 3.77%，是当前精度/体积最优解。
- **速度**：Helio P35 上 RTF 0.635（1.6× 实时），首字 ~950ms，可稳定实时字幕。
- **体积**：APK 250.2 MiB，模型 189.8MB。
- **核心教训**：decoder int8 不可用（自回归反馈放大量化误差），joiner int8 安全；量化必须逐组件验证，不能"全 int8 一刀切"。
- **剩余风险**：0dB 强人声噪声下 CER>50%，需前置 GTCRN 降噪才能覆盖真实嘈杂场景。
